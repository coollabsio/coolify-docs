# Deploy keys

A deploy key grants one SSH key access to one private repository. Use it when you cannot install a Git App or when repository-specific access is preferred.

## Create a deploy key

<Steps>
<Step>

### Generate a key in Coolify

Open **Keys & Tokens > Private Keys**, select **New private key**, then **Generate ED25519** or **Generate RSA**. Coolify saves the key immediately.

Open the saved key's edit icon to give it a name that identifies the repository, select **Save changes**, and copy **Public key**.

</Step>
<Step>

### Add the public key to the repository

Open the repository's deploy-key or access-key settings and add the copied public key.

Keep write access disabled. Coolify only needs to clone and fetch the repository.

</Step>
<Step>

### Copy the SSH repository URL

Use the provider's SSH clone URL:

```sh
git@github.com:coollabsio/coolify-examples.git
```

Do not use the HTTPS URL for **Private Repository (with deploy key)**.

</Step>
<Step>

### Create the application

Open a project, select **+ New**, then **Private Repository (with deploy key)**.

Choose the server, select the stored private key, paste the SSH URL, and configure the application. Use [Smart Scan](/applications/builds/smart-scan) to detect build files and review optional environment-template imports before continuing.

</Step>
<Step>

### Deploy and verify

Select **Deploy**. Confirm the repository clone and requested branch succeed in the deployment log.

</Step>
</Steps>

## Automatic deployments

The SSH key only provides repository access. Choose how the deployment starts.

<Tabs id="deploy-key-automatic-deployment" items={['Repository webhook', 'External workflow']}>
<Tab value="Repository webhook">

Add a [manual Git webhook](/applications/deployments/manual-webhooks), then choose **Deploy on push (webhooks)** under **Advanced > Deployment > Auto deploy**. The provider can then notify Coolify when the configured branch changes.

Use a [GitHub App](/applications/sources/github/app) instead when you want GitHub repository selection and webhook configuration through one integration.

</Tab>
<Tab value="External workflow">

Call the authenticated **Deploy Webhook** from GitHub Actions or another CI system after its checks pass.

The deployment step in the [GitHub Actions example](/applications/sources/github/actions#example-workflow) shows the authentication pattern.

</Tab>
</Tabs>

## SSH host keys

<Callout type="info" title="Host key pinning requires Coolify v4.7.0">
  Coolify pins the SSH host keys of Git hosts in Coolify v4.7.0 or above.
</Callout>

Coolify checks the SSH host key of the Git host on every deployment, so a deployment cannot clone from a host that pretends to be your Git host. For an application that clones over SSH, open the application and select **Git Source** to see the keys in **SSH host keys**.

- **GitHub, GitLab.com, and Bitbucket Cloud**: Coolify accepts only the host keys that the provider publishes. The list shows them with **Published by the provider, used for every deployment**.
- **Other Git hosts**: on the first deployment, Coolify saves the key that the host sends. Later deployments fail if the key changes. This also applies to the hosts of Git submodules.

To save the key of a self-hosted Git host before the first deployment, select **Fetch current host key**. Compare the fingerprint with the fingerprint from the administrator of the Git host, then select **Accept**.

### When a host key changes

The deployment fails, and the deployment log shows that the Git host sent an SSH host key that is not the saved or published key. This can be an attack.

1. Ask the administrator of the Git host if the key changed.
2. Open **Git Source** and select **Fetch current host key** in **SSH host keys**.
3. Select **Accept** only if the fingerprint is the same as the fingerprint from the administrator. Otherwise, select **Decline**.
4. Redeploy the application.

If GitHub or Bitbucket Cloud changes its keys, **Fetch current host key** reads the new keys from the official HTTPS endpoint of the provider. If GitLab.com changes its keys, compare the fingerprint with the keys on [docs.gitlab.com](https://docs.gitlab.com/user/gitlab_com/#ssh-known_hosts-entries?utm_source=coolify.io).

### Add or remove host keys manually

To add a key, select **Edit manually** and enter one line for each key in **Known hosts**, in the format `host key-type key`. Use `[host]:port` for a custom SSH port, for example `[git.example.com]:2222 ssh-ed25519 AAAA...`. Hashed hosts and comments are not supported, and you cannot add keys for GitHub or Bitbucket Cloud. Select **Save changes**.

To remove a saved key, select the delete icon next to it, then confirm **Remove host key**. The next deployment saves the key that the Git host sends then, without a check.

## Key scope

Prefer a separate deploy key for each repository. If a key is exposed, remove it from the repository and Coolify, create a replacement, attach the new key under **Git Source**, and redeploy.
