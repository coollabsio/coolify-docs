# Preview deployments

A preview deployment runs the code from a pull request or merge request separately from the production application. Each preview can use its own domain and environment variables without replacing the production deployment.

Coolify deletes an automatically created preview after its pull request or merge request is closed or merged.

## Before enabling previews

Confirm that the application deploys successfully from its configured branch and that the deployment server has enough capacity to run production and preview containers at the same time.

<Callout type="warning" title="Treat preview code as untrusted">

A pull request can run code on the deployment server. Do not expose production credentials to preview deployments, and keep **PR deployment access** set to **Repository members only** unless you accept the risk of running code from public contributors.

</Callout>

## Enable preview deployments

Open the application, select **Preview Deployments** in its settings sidebar, then select **Enable preview deployments**.

<ZoomImage src="/docs/images/applications/ci-cd/github/preview-deploy/1.webp" alt="Preview Deployments and Allow Public PR Deployments settings" />

With **PR deployment access** set to **Repository members only**, Coolify blocks pull requests from forks unless the author is a repository owner, member, or collaborator. Choose **Public (fork PRs allowed)** only when anyone should be allowed to trigger a preview. GitLab, Gitea, and Bitbucket pull requests from other repositories require public preview deployments to be enabled.

**PR deployment access** applies only while preview deployments are enabled. When they are disabled, a preview that you deploy by hand is deployed as **Repository members only**, and a preview that a webhook queued before you disabled them does not start.

## Configure preview domains

Open **Preview Deployments**. Under **Preview URL template**, **URL template** controls the generated domain:

- `{{pr_id}}` inserts the pull-request or merge-request number.
- `{{random}}` inserts a random value.
- `{{domain}}` inserts the production application's domain name.

The default template is `{{pr_id}}.{{domain}}`.

<ZoomImage src="/docs/images/applications/ci-cd/github/preview-deploy/4.webp" alt="Preview URL Template and Load Pull Requests controls in Coolify" />

For example, `{{pr_id}}.preview.example.com` produces `123.preview.example.com` for pull request 123.

<Callout type="warning" title="Create wildcard DNS before using generated subdomains">

To use domains such as `123.preview.example.com`, create an `A` or `AAAA` record for `*.preview.example.com` that points to the deployment server.

</Callout>

You can also enter a domain for an individual preview. Docker Compose previews can have a separate domain for each service.

## Separate preview variables from production

Coolify keeps production and preview environment variables in separate groups.

<ZoomImage src="/docs/images/applications/ci-cd/github/preview-deploy/2.webp" alt="Production and preview environment variable groups" />

- **Production Environment Variables** apply to the main deployment.
- **Preview Deployment Environment Variables** apply to pull-request and merge-request deployments.

Creating a production variable can also create a preview entry with the same value. Review both groups when adding a credential.

With **PR deployment access** set to **Public (fork PRs allowed)**, a preview does not get the preview variables that have the same value as in production. Coolify compares the values after it resolves shared variables, so a preview variable such as `{{team.API_KEY}}` whose value resolves to the production value is also withheld. The deployment log lists the withheld keys. Give such a variable its own preview value to pass it to the preview.

<Callout type="info" title="Upgrade from Coolify v4.7.6 or earlier">

Since Coolify v4.7.7, a public preview no longer gets a preview variable whose value only resolves to the production value, for example `{{team.KEY}}` or `{{ team.KEY }}`. A public preview that used such a variable does not get it after the upgrade. Give the preview variable its own value.

</Callout>

With **Repository members only**, a preview with at least one runtime preview variable falls back to production runtime values for keys with no preview entry. A public preview does not get this fallback. Previews marked to keep production values, from before Coolify v4.5.1, retain the trusted-preview behavior. This fallback applies only at runtime.

Give previews explicit, limited non-production values for databases, storage, and external services. Deleting a preview variable can expose its production runtime value through fallback. Review the deployment log for keys Coolify withheld. A preview container is temporary, but data written to an external service can remain after Coolify deletes the preview.

Follow [Environment variables](/applications/configuration/environment-variables) for variable scopes and build-time values.

## Preview files on the server

Each preview has its own folder on the deployment server, next to the folder of the application: `/data/coolify/applications/<uuid>-pr-<id>`. The preview keeps its Compose file, its `.env` file, and, with **Preserve repository during deployment**, its checkout of the pull request there. A preview never replaces the repository files or the `.env` file of production.

With **Preserve repository during deployment**, a preview mounts the repository files from its pull request and updates only its own copy of a file storage. Deleting the preview removes its folder. Deleting the application with **Permanently delete all configuration files from the server.** selected also removes the folders of its previews.

## Docker Compose file of a preview

A preview of a Docker Compose application deploys the Compose file of its pull request when all of these apply:

- **PR deployment access** is **Repository members only**.
- The pull-request branch is in the same repository, not in a fork.
- Coolify received the pull request through a webhook or **Load Pull Requests**.
- **Advanced > Docker compose > Compose deployment** is not **Raw (deploy file as-is)**.

The file of the pull request changes only that preview. It does not change the variables or file storages of the application. Coolify resolves the [`include` entries](/applications/builds/docker-compose#include-other-compose-files) of that file in the same way as for production.

Otherwise, for example for a public preview or a preview created through the API, the preview uses the Compose file of the base branch. The deployment log tells why.

## Docker Compose preview names

A Docker Compose preview runs in its own Docker Compose project and network, so its services keep the names from the Compose file. Services reach one another by these names, for example `db`. Additional Compose files, `depends_on`, and custom start commands such as `docker compose up -d web` use the same names in production and in previews. Each service also answers to `<service>-pr-<id>` on the preview network, and its container is named `<service>-<uuid>-pr-<id>`.

A preview renames its services to `<service>-pr-<id>` when it joins a network that production also uses:

- **Advanced > Docker compose > Predefined network** is set to **Connect to predefined network**.
- The Compose file declares a network with `name:` or `external: true`.

On a shared network, Docker resolves a service name to the container of production. For example, `db` in a preview connects to the production database. To connect to the service of the same deployment, use the `SERVICE_NAME_<SERVICE>` variable as the hostname. Its value is `db` in production and `db-pr-<id>` in a preview:

```yaml
services:
  web:
    environment:
      DB_HOST: ${SERVICE_NAME_DB}
```

When a preview on a shared network uses the name of another service as a hostname, Coolify writes a warning to the deployment log.

## Preview container labels

A preview container gets its own proxy labels for the preview domain. It also gets the custom container labels of the application that are not Traefik, Caddy, or `coolify.` labels, for example a `logging` label. Labels that route the production domains are left out.

To protect previews with a password, use [HTTP Basic Authentication](/applications/configuration/general#http-basic-authentication) instead of proxy labels.

## Load pull requests that were already open

Coolify does not automatically deploy pull requests that were open before previews were enabled.

For a GitHub-based application, open **Preview Deployments** and select **Load Pull Requests**. In the **Pull requests** dialog, select **Deploy preview** beside each request that needs a preview. Use **Configure** to prepare a preview without deploying it.

A GitHub App can add the preview deployment status and domain to the pull request, then update the comment when the deployment state changes.

## Deploy a Docker Image preview manually

For a [Docker Image application](/applications/deployments/docker-image), open **Preview Deployments** and use **Manual preview**.

Enter:

- **Preview ID:** a positive whole number used in the preview name, domain, logs, and cleanup
- **Docker tag:** the image tag to deploy, for example `pr_1234`. It must be a valid image tag.

Select **Deploy preview**. This path is useful when an external CI system builds one image tag for each pull request.

## Manage a preview

Open **Preview Deployments** to view each preview. Use **Links** to open its domain or Git request, **Logs** for deployment and runtime logs, and **Actions** for lifecycle actions.

Depending on the preview state, the **Actions** menu shows:

- **Deploy** and **Deploy (without cache)** for a stopped preview
- **Redeploy** and **Redeploy (without cache)** for a running preview
- **Stop** to remove its containers and other non-persistent runtime resources
- **Delete** to permanently remove the preview deployment

When Coolify skips a GitHub pull request preview, for example because of a skip marker, a fork pull request while public PR deployments are off, or no changed file in the watch paths, the deployment history of the preview shows a deployment with the status **Skipped** and the reason.

## Verify the preview lifecycle

1. Open or update a pull request or merge request.
2. Confirm that Coolify creates a separate preview deployment.
3. Open the preview domain and test the proposed change.
4. Close or merge the request.
5. Confirm that Coolify removes the automatically created preview.

## Manage previews through the API

Use `GET /applications/{uuid}/previews` to list previews and `GET /applications/{uuid}/previews/{pull_request_id}` to inspect one. Use `POST /applications/{uuid}/previews` to open or redeploy a preview:

```sh
curl --request POST "https://coolify.example.com/api/v1/applications/<application-uuid>/previews" \
  --header "Authorization: Bearer $COOLIFY_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{"pull_request_id":42,"git_type":"github","force":false}'
```

A token with `deploy` can only redeploy an existing preview without changes. These requests also need `write`:

- open a new preview
- change the preview's `pull_request_html_url`, `git_type`, or `docker_tag`
- choose a `commit`

Without `write`, Coolify returns `403`.

Use the provider that hosts the request. Bitbucket also requires a `commit` SHA. Pull request IDs must be positive integers no greater than `2147483647`; invalid IDs return a validation error, including in the MCP deploy tool.

`POST /deploy` with `pull_request_id` deploys an existing preview. For deploy-key and public-repository applications, it deploys the pull-request ref. For a Docker Image application, `docker_tag` can also open a preview or change its tag, which needs `write`. Gitea previews use the pull request's head commit. The UI's pull-request listing and status updates are available for GitHub App sources.

Inspect deployment history after the request is accepted. Closing or deleting a preview removes only its own containers and Coolify-created networks and volumes.
