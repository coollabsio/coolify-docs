# Deploy applications

A deployment is a queued operation that prepares the required images and applies the application's runtime configuration on the selected server.

The deployment can build images from source, [pull existing images](/applications/deployments/docker-image), or build and pull the images required by services in a Docker Compose definition. Docker creates and runs the resulting containers on your infrastructure.

Read [Build and deployment model](/core/build-deployment-model) for the complete path from source to running containers.

<CoolCallout icon={Refresh23} title="The short version">

Start a deployment manually, from a Git event, or through automation. Use **Deployment Logs** to follow the queue, inspect the exact operation log, and verify the result.

</CoolCallout>

## Start a deployment

| Action | When to use it |
| :--- | :--- |
| **Deploy** | Start the first deployment of a configured application. |
| **Redeploy** | Run the normal deployment flow again for an existing application. |
| **Restart** | Recreate the runtime through the deployment queue. Source-based paths start the existing image when no build setting changed, and build when a build setting changed or the image is no longer on the server. Docker Image pulls the saved image reference again. |
| **Deploy (without cache)** or **Redeploy (without cache)** | Build without Docker build cache. For a custom Docker Compose build command, Coolify adds `--no-cache`. |
| Git webhook | Deploy a new commit received from the connected repository. |
| Deploy webhook or API | Start a deployment from an external CI system or automation. |

A deployment request enters the queue. Coolify records whether it is queued, in progress, successful, failed, or cancelled.

Before a restart, the **Restart** dialog tells you whether the restart builds a new image and which changed setting needs the build.

When the worker that runs a deployment stops, for example because the Coolify host ran out of memory, Coolify fails the deployment after it has no log update for longer than the deployment timeout of the server plus 10 minutes. The next queued deployment then starts.

Deleting an application cancels its queued and running deployments and removes their build containers on the deployment and build servers.

## Inspect deployment history

Open **Deployment Logs** on the application to see previous and active operations.

Open one deployment to inspect its log. The log shows the selected source revision, image build or pull, generated configuration, and container actions. Use the first failing command as the starting point when a deployment does not complete.

A failed source build does not replace the running application. Failures after the build can depend on the replacement path and health-check configuration.
