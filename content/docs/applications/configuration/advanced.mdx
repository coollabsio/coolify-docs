# Advanced settings

Open an application, then select **Advanced** in the application settings sidebar. These controls change build caching, deployment triggers, container names, proxy behavior, restart handling, logging, and GPU access.

The available controls depend on the application's source and build method. A setting that does not apply is hidden.

## Settings available by application type

| Application type | Additional settings shown |
| :--- | :--- |
| Git-based application | Automatic deployments, submodules, Git LFS, and clone depth. Preview controls are on **Preview Deployments**. |
| Docker Compose application | **Raw Compose Deployment** and **Connect To Predefined Network**. GPU controls are hidden. |
| Non-Compose application | GPU controls. |
| Every application | Build, container name, proxy, shutdown, restart, and log-drain controls. |

<Tab value="Build" icon={Code}>

Build controls cache reuse, Docker build arguments, and commit metadata.

<span id="disable-build-cache" />

### Build cache

Under **Build cache**, choose **Rebuild from scratch every time** to prevent Coolify-generated builds from reusing Docker build cache on every deployment.

Choose **Use Docker build cache** for normal deployments. Select **Force deploy (without cache)** instead when only the next deployment needs a clean generated build.

A custom Docker Compose build command controls its own cache flags, so this setting cannot add or remove cache arguments from that command.

---

<span id="inject-build-args-to-dockerfile" />

### Build arguments

**Build arguments** defaults to **Inject build args automatically**. Coolify adds `ARG` instructions for application variables that are available during the build.

Choose **Managed manually in Dockerfile** when the Dockerfile declares and manages every required `ARG` itself. This avoids duplicate injected instructions and gives the Dockerfile complete control over cache boundaries.

---

<span id="include-source-commit-in-build" />

### Source commit availability

Under **Source commit availability**, choose **Available during build** when the image build needs `SOURCE_COMMIT`, the selected Git commit hash.

The default is **Runtime only (preserves cache)** so commits with otherwise identical inputs can reuse cached image layers. `SOURCE_COMMIT` remains available to the running container when it is excluded from the build.

Read [Build cache](/applications/builds/overview#build-cache) before enabling it for every deployment.

</Tab>
<Tab value="Deployment" icon={BranchUp}>

These settings appear only for applications connected to a Git repository.

### Auto Deploy

Under **Deployment**, **Auto deploy** set to **Deploy on push (webhooks)** allows supported Git webhook events to start a deployment. It is enabled by default, but the repository connection must still have a working webhook or provider integration.

Choose **Manual deployments only** when deployments should start only from the Coolify dashboard, API, deploy webhook, or an external workflow.

---

### Preview deployments

Preview enablement and pull-request access are configured on **Preview Deployments** in the application settings sidebar. Select **Enable preview deployments**, then choose **Repository members only** or **Public (fork PRs allowed)** in **PR deployment access**.

Public previews can run contributor-controlled code. Read [Preview deployments](/applications/deployments/preview-deployments) before changing access.

---

</Tab>
<Tab value="Git" icon={BranchUp}>

### Submodules

Under **Git > Submodules**, choose **Clone submodules** when the selected repository commit depends on Git submodules. Coolify includes them during source checkout.

The connected source or deploy key must be able to access every private submodule.

For private submodules in the same GitHub user or organization, prefer a relative URL in `.gitmodules`:

```ini
[submodule "prisma"]
    path = prisma
    url = ../prisma.git
```

The relative URL uses the authenticated parent-repository remote instead of starting a separate unauthenticated HTTPS clone. If checkout still fails, confirm that the GitHub App installation or deploy key can access both repositories.

Changing only the submodule repository does not update the commit recorded by the parent repository. Commit the new submodule pointer in the parent repository before deploying it.

---

### LFS

Under **Git LFS**, choose **Enabled** when the repository stores required files with Git Large File Storage. Coolify downloads the LFS-managed content during source checkout.

Leave it disabled when the build does not need LFS objects.

---

### Shallow Clone

Under **Clone depth**, choose **Shallow clone (latest commit only)** to check out only the latest commit history with `--depth=1`. This can reduce clone time and transferred history for large repositories.

Choose **Full history** when the build needs earlier commits, complete tags, or history-based versioning.

Read [Automatic deployments](/applications/deployments/automatic-deployments) for provider webhook setup.

</Tab>
<Tab value="Docker compose" icon={Code}>

<span id="raw-compose-deployment" />

### Compose deployment

This setting appears only for Docker Compose applications. Coolify normally parses the Compose definition and adds the networking, labels, and other configuration it needs to manage the deployment.

<Callout type="warning" title="Raw mode removes Coolify's Compose changes">

With **Compose deployment** set to **Raw (deploy file as-is)**, Coolify deploys the Compose definition as written. The definition must provide its own proxy labels, networking, and other required runtime configuration.

</Callout>

Read [Raw Compose deployment](/applications/builds/docker-compose#raw-compose-deployment-for-an-application) before enabling it.

---

<span id="connect-to-predefined-network" />

### Predefined network

This setting appears only for Docker Compose applications. Under **Docker compose > Predefined network**, choose **Connect to predefined network** when services in the Compose application must communicate with resources attached to the selected Coolify destination network.

Docker Compose services already receive a private network for communication within their own definition. Joining the predefined network is only needed for communication across Coolify resources, and service DNS names can change after joining it.

Read [Compose networking](/applications/builds/docker-compose#compose-networking) before configuring another resource's hostname.

</Tab>
<Tab value="Container" icon={Box2}>

Container settings control the runtime name assigned to a non-preview application container.

<span id="consistent-container-names" />

### Container naming

Under **Container > Container naming**, choose **Consistent name (no rolling updates)** to use the application UUID as the container name on every deployment.

<Callout type="warning" title="A fixed name disables rolling updates">

Docker cannot run the current and replacement containers with the same name. Enabling this setting prevents Coolify from starting the replacement beside the running container.

</Callout>

Choose **Generated name (rolling updates)** when the application depends on [rolling updates](/applications/deployments/rolling-updates).

---

### Custom Container Name

**Custom container name** appears when consistent naming is selected. Enter a recognizable fixed name when another system must address the container by that exact runtime name.

Coolify converts the value to slug format when you save it. The name must be unique among applications on the same deployment server.

A custom name also disables rolling updates because the current and replacement containers cannot use it simultaneously. Choose generated naming to use deployment-specific names.

### Container name prefix

With consistent naming disabled, set an optional **Container Name Prefix** to make generated names readable while retaining rolling updates. Coolify slugifies the prefix, limits it to 30 characters, and requires it to be unique per server.

| Application | Generated name with prefix `shop-api` |
| :--- | :--- |
| Single container | `shop-api-20260908T141530` |
| Compose service `web` | `web-shop-api-20260908T141530` |

Without a prefix, generated names use the application UUID followed by the timestamp. Old timestamp suffixes remain recognized. In consistent mode, a custom name produces `shop-api` for a single container or `web-shop-api` for the Compose service.

The API field is `custom_container_name_prefix`. Setting `custom_internal_name` enables consistent naming; combining it with `is_consistent_container_name_enabled: false` returns `422`. Applications whose stored custom names were previously applied despite consistent naming being disabled are migrated to consistent mode to preserve their names.

</Tab>
<Tab value="Proxy" icon={Globe3}>

Proxy settings change labels generated by Coolify Proxy for the application's configured domains.

<span id="force-https" />

### HTTPS redirection

Open **Domains** and choose **Enabled** in **Redirect HTTP to HTTPS**. This control appears when an HTTPS domain is configured and labels are managed by Coolify.

The domain, DNS, and certificate must already support HTTPS. Selecting this option does not convert an HTTP-only domain into an HTTPS domain.

---

<span id="enable-gzip-compression" />

### Gzip compression

Choosing **Enabled** in **Gzip compression** allows Coolify Proxy to compress supported responses.

Choose **Disabled** when the application already compresses responses or when a streaming or binary workload should not be compressed by the proxy.

---

<span id="strip-prefixes" />

### Path prefixes

Under **Path prefixes**, choose **Strip prefixes** when the application is exposed under a path but should receive the request without that routing prefix. For example, a request to `/api/users` can be forwarded to the container as `/users`.

Test application routes after changing this setting because the application may generate links or redirects that still include the original prefix.

<Callout type="info" title="Manual labels control these settings">

Proxy controls are unavailable when **General > Container labels > Label management** is set to **Managed manually (edit labels yourself)**. In manual-label mode, change the equivalent proxy labels yourself.

</Callout>

</Tab>
<Tab value="Operations" icon={Settings}>

Operations controls graceful shutdown, crash restart limits, log forwarding, and when changes reach the running container.

### Stop Grace Period (seconds)

Coolify waits for the application process to stop gracefully during rolling updates, manual stops, and restarts.

**Accepted values:**

- Leave the field empty to use the 30-second default.
- Enter a whole number from `1` to `3600` seconds.

Give the process enough time to finish in-flight work after receiving its shutdown signal. Increasing the value does not fix a process that ignores the signal.

---

### Max Restart Count

**Max Restart Count** limits how many times Coolify automatically restarts a crashing application before stopping it and sending a notification.

**Accepted values:**

- The default is `10` restarts.
- Enter `0` to disable the limit.
- Enter a positive whole number to set another limit.

---

### Apply changes

Most dropdowns save immediately. Edited fields such as the container name, stop grace period, restart count, and GPU configuration use **Save changes**.

Redeploy or restart the application after changing a setting that affects the image, container name, proxy labels, network, shutdown behavior, logging, or GPU access.

</Tab>
<Tab value="Logs" icon={Settings}>

<span id="drain-logs" />

### Log drain

Under **Logs > Log drain**, choose **Enabled** to forward application logs to the log-drain endpoint configured on the deployment server.

Coolify rejects the setting when log draining is not enabled on that server. Follow [Log drains](/core/observability/log-drains/overview) before enabling it for the application.

</Tab>
<Tab value="GPU" icon={Server}>

GPU controls appear only for non-Compose applications. The deployment server must already have working GPU drivers and a container runtime configured for GPU access.

<span id="enable-gpu" />

### GPU access

Under **GPU > GPU access**, choose **Enabled** to add GPU access to the application container. Additional GPU fields appear after it is enabled.

---

### GPU Driver

**GPU Driver** selects the container runtime's GPU driver. Enter the driver configured on the deployment server.

---

### GPU Count and device IDs

Use **GPU Count** to request a number of GPUs. Leave it empty to make all available GPUs accessible to the container.

Use **GPU Device Ids** to select specific devices as a comma-separated list, such as `0,2`.

Do not set **GPU Count** and **GPU Device Ids** together. Coolify rejects the configuration and clears both values when both are provided.

---

### GPU Options

**GPU Options** accepts additional driver-specific runtime options. Add only options supported by the GPU driver and container runtime installed on the deployment server.

Select **Save changes**, then redeploy or restart the application and verify GPU access from inside the container.

</Tab>
