# Multi-tenant SaaS domains

A multi-tenant SaaS can let each customer use a domain they own, such as `portal.customer.example`, while every domain routes to the same application in Coolify. The application reads the request hostname and selects the matching tenant.

Coolify manages the proxy route and TLS certificate after you add the complete HTTPS URL to the application. Your SaaS still needs to verify that the customer controls the domain, track its onboarding state, and reject hostnames that are not assigned to a tenant.

<Callout type="info" title="This guide is for self-hosted Coolify">
These instructions assume the application uses Coolify's integrated Traefik or Caddy proxy. With **Custom (None)**, your own proxy must create the route and manage its certificate.
</Callout>

## How the request is routed

For every customer domain, the complete flow is:

1. The customer adds a DNS record that points their hostname to the server running the application.
2. Your SaaS verifies a unique DNS record to confirm that the customer controls the hostname.
3. An operator or your control plane adds `https://<customer-domain>` to the Coolify application.
4. Coolify generates a hostname route for Traefik or Caddy when the application is redeployed.
5. The proxy obtains a certificate from Let's Encrypt and terminates TLS.
6. The proxy forwards the request to the application and preserves the `Host` header.
7. The application resolves that hostname to a tenant.

All customer domains can target the same application and container port. You do not need one Coolify application per tenant unless tenants run separate code, configuration, or compute resources.

<Callout type="warning" title="DNS resolution is not domain ownership verification">
Do not let an unauthenticated customer add arbitrary domains directly to Coolify. Verify control with a unique DNS `TXT` record before creating the route. This prevents a customer from claiming a hostname that belongs to someone else.
</Callout>

## Prepare the application and server

Before onboarding customer domains:

- Run the SaaS as a Coolify application with the integrated proxy enabled.
- Open inbound TCP ports `80` and `443` on the application server.
- Make sure the application listens on the configured container port.
- Configure the application to trust the proxy and resolve tenants from a normalized hostname.
- Reject unknown hostnames instead of serving a default tenant.
- If you will use the API, [enable API access](/api/ip-allowlist) and create a team-scoped token with `write` permission.

The application should normalize hostnames to lowercase, remove a trailing dot, and handle an optional port before performing an exact lookup. Store every hostname with a unique constraint so two tenants cannot claim the same value.

## Give the customer DNS instructions

Ask the customer to choose one hostname. A subdomain is usually the easiest option.

| Customer choice | DNS record | Value |
| :--- | :--- | :--- |
| `portal.customer.example` | `CNAME` | A stable hostname that resolves to the Coolify application server |
| `portal.customer.example` | `A` and optional `AAAA` | The public IPv4 and IPv6 addresses of the application server |
| `customer.example` at the zone apex | `A` and optional `AAAA` | The public addresses of the application server |

Some DNS providers support `ALIAS`, `ANAME`, or CNAME flattening at the zone apex. Those provider-specific records can replace an apex `A` record.

Also ask the customer to add a unique ownership record generated by your SaaS:

```plaintext
_your-saas-verification.portal.customer.example TXT "verify_7f4d2a..."
```

Check the authoritative DNS response rather than a browser or local hosts file. Require the expected token and confirm that the application hostname resolves to the intended server before continuing.

<Callout type="warning" title="Check every published address">
An old `AAAA` record can send IPv6 clients and ACME validation to the wrong server even when the `A` record is correct. Remove incorrect records before activating the domain.
</Callout>

If the hostname uses a CDN or an HTTP proxy, start with proxying disabled until the first certificate has been issued. The CDN must forward traffic for ports `80` and `443` to the Coolify server if you enable it later.

## Add customer domains in the UI

Use the UI for manual onboarding or a small number of domains.

<Steps>
<Step>

### Verify the customer domain

Confirm that the unique `TXT` record matches the token issued for this tenant. Then confirm the application hostname resolves to the server running the Coolify application.

</Step>
<Step>

### Add the HTTPS URL

Open the application and select **Configuration > General**. Add the complete URL to **Domains**:

```plaintext
https://portal.customer-one.example,https://app.customer-two.example
```

Keep the application's existing domains in the field. Separate URLs with commas. If the container listens on a port other than `80`, include that internal port in each URL, for example `https://portal.customer.example:3000`.

For Docker Compose, use **Domains for `<service>`** on the service that receives the request.

</Step>
<Step>

### Save and redeploy

Select **Save**, then redeploy the application. Coolify updates the generated proxy configuration as part of the deployment.

</Step>
<Step>

### Verify routing and TLS

Check DNS, the certificate, and the application response:

```sh
dig +short portal.customer.example
curl -I https://portal.customer.example
openssl s_client -connect portal.customer.example:443 \
  -servername portal.customer.example </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

Confirm that the SaaS resolves the request to the expected tenant before marking the domain active.

</Step>
</Steps>

## Automate onboarding with the API

Use a server-side worker or control plane for ongoing domain onboarding. Never put the Coolify API token in browser code or give it to customers.

The application update endpoint requires a token with `write` permission. Set these values in the trusted worker environment:

```sh
export COOLIFY_URL="https://coolify.example.com"
export COOLIFY_TOKEN="<team-scoped-api-token>"
export APPLICATION_UUID="<application-uuid>"
```

The `domains` field is the complete comma-separated domain set for the application. Updating it replaces the previous value, so read and lock your own canonical domain list before sending an update. Do not send only the newly added domain.

```sh
curl --request PATCH \
  --url "$COOLIFY_URL/api/v1/applications/$APPLICATION_UUID" \
  --header "Authorization: Bearer $COOLIFY_TOKEN" \
  --header "Accept: application/json" \
  --header "Content-Type: application/json" \
  --data '{
    "domains": "https://saas.example.com,https://portal.customer-one.example,https://app.customer-two.example"
  }'
```

Coolify rejects invalid URLs with `422 Unprocessable Entity`. It returns `409 Conflict` when a domain is already assigned to another resource in the team. Do not use `force_domain_override` for normal customer onboarding. Resolve the conflict instead.

Redeploy after the update so the running container receives the new proxy labels:

```sh
curl --request POST \
  --url "$COOLIFY_URL/api/v1/applications/$APPLICATION_UUID/restart" \
  --header "Authorization: Bearer $COOLIFY_TOKEN" \
  --header "Accept: application/json"
```

The restart operation requires `deploy` permission. Use a separate deploy token or a carefully protected `root` token if one worker performs both operations. Read [API permissions](/api/permissions) before choosing the token scope.

For a Docker Compose application, send `docker_compose_domains` instead of `domains`. Each entry identifies the Compose service and its complete domain set. Follow the schema shown by the **Update an application** endpoint in the API reference.

## Use a safe onboarding state machine

DNS changes, deployments, and certificate issuance are asynchronous. Treat onboarding as a retryable workflow rather than one request that must finish immediately.

| State | Control-plane action |
| :--- | :--- |
| `pending_dns` | Show the required routing and ownership records. |
| `verifying` | Resolve authoritative DNS and compare the unique ownership token. |
| `configuring` | Add the verified hostname to the canonical list and update Coolify. |
| `deploying` | Restart the application and wait for the deployment to finish. |
| `checking_tls` | Request the HTTPS URL and inspect the served certificate. |
| `active` | Allow the application to resolve the hostname to the tenant. |
| `failed` | Store a specific error and retry only retryable steps. |
| `removing` | Remove the hostname from Coolify, redeploy, then remove the tenant mapping. |

Serialize updates for each Coolify application. Two workers that read the same domain list and write different additions can otherwise overwrite each other. Make retries idempotent by deriving the submitted domain list from a database table with a unique normalized hostname.

For removal, stop resolving the hostname to the tenant first or return a neutral response. Then remove it from the canonical Coolify domain list and redeploy. Certificate files may remain in proxy storage until normal cleanup, but the removed hostname no longer has an active router.

## What Coolify configures in the proxy

You normally should not add these rules by hand. The simplified examples explain the pieces Coolify generates and may differ from the exact labels on a running container.

With Traefik, each HTTPS hostname needs a router, a target service, TLS, and a certificate resolver:

```yaml
labels:
  - traefik.enable=true
  - traefik.http.routers.tenant-customer.rule=Host(`portal.customer.example`)
  - traefik.http.routers.tenant-customer.entrypoints=https
  - traefik.http.routers.tenant-customer.tls=true
  - traefik.http.routers.tenant-customer.tls.certresolver=letsencrypt
  - traefik.http.services.saas.loadbalancer.server.port=3000
```

With Caddy Docker Proxy, the hostname and reverse proxy target are expressed as container labels. Caddy obtains and renews the certificate automatically:

```yaml
labels:
  caddy: portal.customer.example
  caddy.reverse_proxy: "{{upstreams 3000}}"
```

Coolify derives equivalent labels from **Domains**, keeps them attached to the deployed resource, connects the proxy to the required Docker network, and persists the proxy's ACME state. Editing generated labels manually makes the UI domain controls read-only and moves responsibility for routing to you.

## Certificate behavior and limits

Adding an `https://` domain tells the integrated proxy to request a certificate. The proxy, not the application, completes the ACME challenge, stores the certificate, serves it through SNI, and renews it before expiry.

Keep these constraints in mind:

- The hostname must resolve to the proxy before certificate issuance can succeed.
- Ports `80` and `443` must reach the same Coolify proxy.
- A restrictive CAA record must permit Let's Encrypt.
- Let's Encrypt applies issuance and failed-validation rate limits. Do not repeatedly redeploy an invalid hostname.
- A wildcard certificate for your own SaaS domain does not cover domains owned by customers. Each customer hostname needs a matching certificate.
- Traefik and Caddy persist ACME data on the server. Back up proxy state and avoid running two independent proxies that issue for the same hostname without coordination.

At high domain counts, queue activations, apply a short retry backoff, and monitor proxy logs for ACME errors. Domain count alone does not require one application per customer, but certificate-authority limits and large proxy configurations still need operational monitoring.

## Troubleshoot onboarding

| Symptom | Check |
| :--- | :--- |
| Domain resolves but returns `404` | Confirm the complete URL remains in **Domains** and the application was redeployed. |
| `502` or `504` response | Confirm the application is healthy and the domain targets the correct internal container port. |
| Wrong tenant loads | Normalize the `Host` value, require an exact mapping, and reject unknown hostnames. |
| Certificate warning | Check `A`, `AAAA`, CAA, ports `80` and `443`, CDN settings, and proxy ACME logs. |
| API returns `409` | Find the other Coolify resource using the domain and remove the conflict. |
| One automated addition disappears | Serialize updates and send the complete canonical domain set in every PATCH request. |
| Works over IPv4 but not IPv6 | Correct or remove the hostname's `AAAA` record. |

For deeper checks, use [Domains](/core/networking/domains), [DNS configuration](/core/networking/dns), and [Let's Encrypt not working](/troubleshoot/dns-and-domains/lets-encrypt-not-working).
