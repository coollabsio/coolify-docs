# Environment variables

Application environment variables pass configuration to the image build, the running container, or both.

Open the application, then select **Environment Variables**.

<Callout type="info" title="Preview deployments have separate values">

Production and preview variables appear in separate labelled sections. Use the preview section for values that should differ, such as a preview database or callback URL. Check the [runtime fallback rules](/applications/deployments/preview-deployments#separate-preview-variables-from-production) before deleting a preview value.

</Callout>

<span id="developer-view" />

## Add variables

Use **Normal view** to configure one variable at a time. Select **Add**, enter **Name** and **Value**, choose its scope and value settings, then select **Add variable**. Select a variable name or its edit icon to change it, then select **Update variable**.

Use **Developer view** to paste or edit multiple values in `.env` format:

```dotenv
NODE_ENV=production
LOG_LEVEL=info
API_URL=https://api.example.com
```

Lines beginning with `#` are ignored, except `# coolify:` lines. Saving Developer view creates, updates, and removes entries to match its contents, and sets the order of the variables to the order of the lines.

As in a `.env` file, Developer view removes the spaces around an unquoted value. Put the value in quotes to keep its spaces, for example `GREETING=" hello "`.

Locked secrets and multiline values cannot be edited in Developer view. Change those entries in Normal view.

For a Docker Compose application, an empty variable with a default in the Compose file gets a `# Compose default: <value>` line above it. The deployment uses that default while the value is empty. Coolify ignores this line when you save.

### Set flags in Developer view

To set the flags of a variable, put a `# coolify:` line directly above the variable line:

```dotenv
# coolify: literal buildtime=false
DATABASE_URL=postgres://db:5432/app
```

| Flag | Default | Meaning |
| :--- | :--- | :--- |
| `literal` | `false` | Keep `$` references as text. |
| `buildtime` | `true` | Make the variable available during the build. |
| `runtime` | `true` | Make the variable available in the running container. |

- Write a flag name alone to set it to `true`, or write `=true` or `=false`.
- Developer view shows a `# coolify:` line only for variables whose flags are not the defaults.
- If a variable has no `# coolify:` line, its flags do not change when you save. A new variable without this line gets the defaults.
- The `# coolify:` line must be directly above the variable line. A blank line, another comment, or a second `# coolify:` line between them stops the save with an error. An unknown flag or a value other than `true` or `false` also stops the save. When the save stops, nothing changes.
- A `# coolify:` line above a locked or multiline variable has no effect.

## Environment values in logs

An Owner or Admin can change **Environment values in logs** on the resource's **Environment Variables** page. Applications, services, and standalone databases each have this setting.

| Option | Effect |
| :--- | :--- |
| **Hide all values** | Default. Adds the resource's environment values to log redaction. |
| **Hide locked values only** | Allows ordinary environment values in logs while retaining redaction for locked values and recognized secret formats. |

The setting applies to deployment logs, scheduled-task output, copied or downloaded logs, and logs returned through the API and MCP. It does not change live log streaming or scrub the application's own stored logs or external log drains.

Redaction is best effort. Exact matching for ordinary unlocked values uses a minimum length of eight bytes; short or transformed values can remain visible. Locked and resolved remote secrets receive stricter matching, but a failed secret-provider lookup can prevent redaction of its resolved value. Avoid writing secrets to logs in the workload itself.

Through the application, database, or service API, set `redact_all_env_values_in_logs` to `true` for all values or `false` for locked values only. Changing this field requires team administrator permissions.

## Build and runtime scope

**Build time** and **Runtime** are independent dropdowns. New variables default to **Available during build (a change needs a rebuild)** and **Available in the container**.

| Setting | Image build | Running container |
| :--- | :---: | :---: |
| Build and runtime | Available | Available |
| Build only | Available | Not available |
| Runtime only | Not available | Available |

Set **Build time** to **Not available during build** for a secret that the application only reads after the container starts.

### Build secrets

**Build secrets** controls how build-time variables get to the build:

| Option | How values get to the build | Values in the image |
| :--- | :--- | :--- |
| **Docker BuildKit secrets** | Coolify mounts each value as a BuildKit secret on every `RUN` instruction, as an environment variable with the same name. | Not saved. |
| **Standard build arguments** | Coolify passes each value as `--build-arg` and adds `ARG` lines after each `FROM`. | Docker saves the values in the image history. Anyone who can pull the image can read them. |

New applications use **Docker BuildKit secrets**. Applications created before this default keep their setting. The [Recommended settings](/applications/configuration/recommended-settings) page recommends build secrets for them.

If the build server does not support Docker BuildKit secrets, Coolify uses build arguments for that deployment.

BuildKit secret mounts are temporary, but a build command can still print a secret or write it to an image file or build artifact. For example, Next.js embeds statically referenced `NEXT_PUBLIC_*` values in browser JavaScript, so never use a `NEXT_PUBLIC_*` variable for a secret.

<Callout type="warning" title="Values are available only inside RUN">

With build secrets, a Dockerfile can read the values only in `RUN` instructions. Instructions such as `FROM node:${NODE_VERSION}`, `COPY --chown=$APP_USER`, or `WORKDIR $APP_DIR` get empty values, and the deployment log shows a warning. A `# syntax=docker/dockerfile:1.x` line must use version 1.10 or later. To use these variables outside `RUN`, set **Build secrets** to **Standard build arguments**.

</Callout>

### Example: private npm registry

Authenticate to a private npm registry during the build with a build variable instead of committing a token to the repository.

1. Add an `.npmrc` file to your project root:

   ```ini
   //registry.npmjs.org/:_authToken=${NPM_TOKEN}
   ```

2. Add `NPM_TOKEN` with **Build time** set to **Available during build** (the token is only needed during `npm install`), with **Runtime** set to **Not available in the container**, and set its value to your registry token.

3. Deploy the application. The build reads `NPM_TOKEN` and authenticates to the registry.

## Multiline and literal values

Set **Value type** to **Multiline** when a value contains line breaks, such as a private key, certificate, or configuration file.

Set **Interpolation** to **Literal (keep $ characters as-is)** when characters such as `$` must remain unchanged. Without it, Coolify can expand references contained in the value. Multiline values are already treated literally.

Coolify saves a value with more than one line exactly as you enter it, in the UI and in the API, including a trailing newline. For a single-line value, Coolify removes only the line breaks around it and keeps leading and trailing spaces and tabs. The **Value** field shows a warning when the value starts or ends with a space.

Coolify refuses a value with a NUL character when you save it, because a container cannot start with one.

<Callout type="info" title="Save older multiline values again">

Before v4.7.0, Coolify removed the trailing newline of multiline values. Some tools reject such a value, for example OpenSSH rejects a private key with `error in libcrypto`. Enter the value again and save it to restore the newline.

</Callout>

## Lock a variable

Select **Lock** on a variable, then confirm, to hide its value. After you lock a variable, nobody can see or copy its value in the UI or the API.

A lock is permanent. You cannot unlock the variable in the UI, the API, or MCP. To change a locked value, enter a new value in **Value** and select **Update variable**. Leave **Value** empty to keep the current value.

## Shared variables

Reference a team, project, environment, or server variable instead of copying the same value into every resource:

```sh
{{environment.DATABASE_URL}}
```

Follow [Shared variables](/core/team/shared-variables) to create a value at the correct scope and assign it to an application variable.

## External secret managers

Link Doppler, Infisical, or HashiCorp Vault and reference a remote value with `{{vault.KEY}}`. Follow [Use a secret manager](/integrations/security/using-secret-managers).

## Predefined application variables

Coolify makes deployment information available through predefined values.

| Variable | Value |
| :--- | :--- |
| `COOLIFY_FQDN` | Application domain names. |
| `COOLIFY_URL` | Application URLs. |
| `COOLIFY_BRANCH` | Selected Git branch. |
| `COOLIFY_RESOURCE_UUID` | Coolify resource identifier. |
| `COOLIFY_CONTAINER_NAME` | Generated container name. |
| `SOURCE_COMMIT` | Deployed Git commit. |
| `PORT` | First exposed port when `PORT` is not already set. |
| `HOST` | `0.0.0.0` when `HOST` is not already set. |

Coolify excludes `SOURCE_COMMIT` from Docker builds by default to preserve cache reuse. Set **Advanced > Build > Source commit availability** to **Available during build** when the build needs it.

Assign a predefined value to your own key when the application expects another name:

```dotenv
APP_REVISION=$SOURCE_COMMIT
```

## Docker Compose variables

Coolify detects variable references in a Compose definition and displays them as application variables:

```yaml
services:
  api:
    environment:
      DATABASE_URL: ${DATABASE_URL}
      LOG_LEVEL: ${LOG_LEVEL:-info}
      API_KEY: ${API_KEY:?}
```

`${API_KEY:?}` marks the variable as required. Coolify blocks deployment while its value is empty.

For generated stack values such as URLs, users, passwords, and random strings, read [Docker Compose](/applications/builds/docker-compose).

## Apply changes

Save the variables, then redeploy or restart the application so Coolify recreates the runtime environment.

Use a new deployment when build-time values changed. Use **Restart** when only runtime values changed. Source-based paths reuse an existing image when eligible; Docker Image pulls the saved image reference again.

A change to a variable that is available during the build needs a new build, because the variable can change the image. The **Changes pending** popover marks such changes, and the **Restart** dialog tells you when a restart builds a new image and why.

## Variable order

**Environment variable order** sets the order of the list and of the `.env` file that a deployment writes:

- **Creation order** writes the variables in the order of the **Environment Variables** page. Change the order in **Developer view**.
- **Alphabetical** sorts the variables by name.

A variable can reference a variable that comes before it in the `.env` file. Keep the referenced variable above the variable that uses it.

Docker Compose applications do not show this setting.

## Names and copying values

New environment variable names must match `[A-Za-z_][A-Za-z0-9_.]*`: begin with a letter or underscore, then use letters, numbers, underscores, or dots. Existing invalid runtime-only names, such as `my-var`, deploy with a warning and suggested name. Invalid build-time names stop the image build.

Use the copy button to copy a resolved value. Shared-variable and `$SERVICE_*` references resolve to their actual values. Locked variables have no copy button, and references to locked shared variables remain references rather than exposing the secret.
