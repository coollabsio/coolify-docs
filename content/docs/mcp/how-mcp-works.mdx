# How MCP works

Coolify exposes an MCP server at `/mcp`. An MCP-compatible client sends Streamable HTTP requests to that endpoint with a Coolify API token.

## Connection flow

1. Enable MCP for the Coolify instance.
2. Keep MCP enabled for the team the token belongs to.
3. Create an API token for that team.
4. Configure the client with the endpoint and Bearer token.
5. The client negotiates MCP capabilities and calls tools, reads resources, or uses prompts.

## Authentication and scope

The client sends the complete token as a Bearer credential:

```http
Authorization: Bearer 67|abcthisisa123dummytoken
```

The token is bound to one Coolify team. MCP only returns resources owned by that team. Create one token per team when a client needs access to multiple teams.

The instance MCP setting must be enabled before `/mcp` responds. Team owners can disable MCP for individual teams. A disabled instance returns `404`; a disabled team returns `403`.

On self-hosted instances, **Allowed API IPs** applies to MCP requests. The **MCP server** switch controls `/mcp` independently of REST **API access**.

## MCP primitives

<Tabs items={['Tools', 'Resources', 'Prompts']}>
<Tab value="Tools">

Tools perform Coolify queries and operations. Read tools need `read`; deployment and lifecycle tools need `deploy`; resource creation and configuration changes need `write`. Tools and actions are hidden when the token lacks the required permission. Management tools use the same validation, team scope, and permissions as the REST API. [MCP capabilities](/mcp/capabilities/overview) groups tools by task.

</Tab>
<Tab value="Resources">

Resources are read-only addresses that an MCP client can request directly. Coolify currently exposes an infrastructure overview and application summary resources.

</Tab>
<Tab value="Prompts">

Prompts give clients guided workflows. Coolify provides prompts for troubleshooting applications and explaining failed deployments.

</Tab>
</Tabs>

## Response boundaries

Coolify returns structured responses with `data` and may include `_pagination`, `_actions`, or failure details. Inspection tools hide environment values and sensitive configuration. `get_env_values` explicitly reads values with `read` and `read:sensitive` for an Admin or Owner; locked values are never revealed. Some management responses include supported sensitive configuration only with `read:sensitive`. Private keys, tokens, passwords, and webhook URLs remain excluded. Full deployment logs are not returned; optional summaries are capped and best-effort redacted.
