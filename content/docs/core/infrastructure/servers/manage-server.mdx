# Manage a server

Open **Servers**, select a server, then open **General** to manage its identity, SSH connection, domain defaults, and role.

<Callout type="warning" title="Connection changes can make the server unreachable">
Before changing the IP address, domain, SSH user, port, or connection timeout, confirm that the new connection works from the Coolify machine.
</Callout>

## General settings

| Setting | What it controls |
| :--- | :--- |
| **Name** | The name shown for the server in Coolify. |
| **Description** | Optional notes about the server or its purpose. |
| **Wildcard domain** | The base domain Coolify can use when suggesting domains for new resources. |
| **IP address or domain** | The address Coolify uses for SSH and server communication. |
| **SSH user** | The account Coolify uses for SSH. |
| **SSH port** | The SSH port. |
| **Connection timeout** | How long Coolify waits for the SSH connection, from 1 to 300 seconds. |
| **Server timezone** | The timezone used for scheduled operations such as backups and cron jobs. |
| **Server role** | Choose **Deployments only**, **Builds only**, or **Deployments and builds**. See [Server roles](/core/infrastructure/servers/build-servers#server-roles). |

Select **Save changes** after changing fields that do not save automatically. If you changed the connection, run the server validation again to confirm Coolify can still reach it.

You cannot switch a server with managed resources to **Builds only**. Move or delete those resources first. The role cannot change while GitHub Actions runners are enabled. Read [Build Servers](/core/infrastructure/servers/build-servers) before changing the role.

### Wildcard domain

For example, setting **Wildcard domain** to `https://example.com` lets Coolify suggest a domain such as `https://<application-id>.example.com` for a new resource.

Create a DNS record for `*.example.com` that points to this server. Changing the setting does not create DNS records or update domains already assigned to resources.

## Server details

After successful validation, the **Server overview** section of the **General** page displays detected information such as:

- operating system
- CPU architecture and core count
- memory
- kernel version
- Docker versions

Coolify refreshes this information when it validates or checks the server. To refresh it yourself, select **Fetch server details**, or **Refresh details** when details already exist. For a server linked to a cloud provider, this action also refreshes the status at the provider. It refreshes the provider status also when the server is not validated yet.

Use this information to confirm that the connected machine and its available resources match what you expect.

## Link an existing server to a cloud provider

If you added a Hetzner, DigitalOcean, Vultr, or Hostinger server manually, you can link its Coolify record to the matching provider machine.

Linking lets Coolify read provider status and display provider-backed actions such as **Power On** when a Hetzner, DigitalOcean, or Vultr machine is stopped. It does not create a new machine.

<Steps>
<Step>

### Add the provider token

Follow [Cloud Tokens](/core/security/credentials/cloud-tokens) to add a token for the account containing the server.

</Step>
<Step>

### Open the linking flow

1. Open **Servers** and select the server.
2. Open **General**.
3. In the **Connection** section, select **Link provider**.
4. Choose **Hetzner**, **DigitalOcean**, **Vultr**, or **Hostinger**.
5. Select the matching provider token.

</Step>
<Step>

### Find the provider machine

Enter the provider ID of the machine and select **Search ID**, or select **Search by server IP**. The ID field is **Server ID** for Hetzner, **Droplet ID** for DigitalOcean, **Instance ID** for Vultr, and **Virtual Machine ID** for Hostinger.

Confirm that **Match found** shows the intended machine, then select **Link resource**.

</Step>
<Step>

### Confirm the link

Return to the server page and confirm that the **Server overview** section shows a badge with the provider and its status, for example `Hetzner · Running`. If the status is stale, select **Refresh details** before taking a provider-backed action.

Coolify does not validate a linked Hostinger server over SSH while the VPS is stopped or suspended. Start the VPS in hPanel first.

</Step>
</Steps>

<Callout type="warning" title="Match the server carefully">
Link only the provider machine represented by this Coolify server record. Provider-backed actions and deletion options apply to the linked machine.
</Callout>

## Revalidate after connection changes

Run validation again after changing:

- IP address or domain
- SSH user or port
- network routing, firewall rules, or tunnel configuration

If the connection fails, restore the previous settings or use the provider console to correct SSH access. Follow [OpenSSH](/core/infrastructure/servers/openssh) and [Firewall](/core/infrastructure/servers/firewall) for the common checks.

## Build and deployment limits

Open **Advanced** to control how many deployments a server runs at once and how long each deployment may run.

| Setting | What it controls | Default |
| :--- | :--- | :--- |
| **Concurrent builds** | How many deployments can build at the same time on this server. Raise it to deploy more resources in parallel; lower it to protect a small server from resource exhaustion during builds. | `2` |
| **Deployment timeout** | The maximum time a single deployment may run before Coolify cancels it. Increase it for large images or slow builds that legitimately exceed the limit. | `3600` |
| **Queue limit** | The maximum number of deployments allowed to wait in the queue. When the limit is reached, Coolify rejects new deployments with an HTTP `429` response. | `25` |

Select **Save changes** after changing these values.

<Callout type="info" title="Limits are per server">
The concurrent-build count and queue limit apply to each server independently. A build counts on the server that runs it: the deployment server, or the [build server](/core/infrastructure/servers/build-servers) that builds the image. When a deployment starts, it reserves a build server with a free slot. When a build server slot is free again, the waiting deployments of other servers can start.
</Callout>

## Disk usage notifications

Set the high-disk notification interval under **Advanced**. Alerts repeat at most once per interval per server, with a default of 24 hours. If usage falls at least five percentage points below the threshold and later rises above it, Coolify can alert sooner. The API field is `server_disk_usage_notification_interval_hours`.

A server becomes unreachable after two consecutive failed connection checks. A single failed check does not mark every resource as exited; deployment attempts recheck servers marked unreachable before failing.
