# Email

Coolify can send team notifications through a hosted email service, a team-specific SMTP server, or Resend. Self-hosted teams can also reuse the transactional email provider configured for the entire Coolify instance.

Open **Notifications > Email** to configure the channel.

<Callout type="info" title="Instance-wide email is self-hosted only">
The **Email service > Use system-wide settings** option appears only on self-hosted Coolify. It uses the provider configured under [**Settings > Email**](/core/instance-management/instance-settings#email-delivery) for the Coolify instance. When the instance has a [notification sender](/core/instance-management/instance-settings#notification-sender), team notifications come from that sender.

Coolify Cloud shows **Use hosted email service** instead. Cloud users do not configure the instance-wide provider.
</Callout>

## Choose an email provider

The available choices depend on how you use Coolify:

| Provider | Availability | What you need |
| :--- | :--- | :--- |
| **Use hosted email service** | Coolify Cloud | No provider credentials. |
| **Use system-wide settings** | Self-hosted Coolify | A working email provider under **Settings > Email**. |
| **SMTP** | Coolify Cloud and self-hosted Coolify | One or more SMTP servers, each with a sender, host, port, encryption, and optional authentication details. |
| **Resend** | Coolify Cloud and self-hosted Coolify | A Resend API key, a sender name, and a sender address. |

Only one provider sends the team's email. Under **Email provider**, select **None**, **SMTP**, or **Resend**. When you change **Email service**, Coolify turns off the team's SMTP or Resend provider. After you change back to **Use team email settings**, select the provider again.

Before you start, prepare the values required by the option you plan to use:

- For **SMTP**, copy the host, port, encryption method, username, and password from your email provider. Confirm that the provider permits the sender address you want to use.
- For **Resend**, verify your sending domain in Resend and create an API key.
- For **system-wide email**, configure and test the instance provider first. This requires access to the self-hosted instance settings.

## Use the hosted or system-wide provider

The dashboard shows the option for your Coolify deployment type. It does not show both options together.

<Tabs id="notification-email-deployment-type" items={['Self-hosted', 'Coolify Cloud']}>
<Tab value="Self-hosted" icon={Server}>

<Steps>
<Step>

### Configure the instance provider

As an instance administrator, open [**Settings > Email**](/core/instance-management/instance-settings#email-delivery). Select **SMTP** or **Resend** next to **Email delivery**, enter its settings, and save. Optionally, set a [notification sender](/core/instance-management/instance-settings#notification-sender) for team notifications.

Use **Send test** on the instance settings page. Continue only after that test arrives. This confirms that the instance-wide provider works before a team tries to reuse it.

</Step>
<Step>

### Reuse it for the team

Open **Notifications > Email** for the team and set **Email service** to **Use system-wide settings**.

The team now uses the instance provider and sender. It does not receive its own copy of those credentials, and team members cannot change them from the Notifications page.

</Step>
<Step>

### Choose events and test the team channel

Select the events to send by email under **Notification events**. Then select **Send test**, enter a recipient address you can access, and send the test.

</Step>
</Steps>

Event selections and the test recipient remain specific to this team. Changing the instance-wide provider affects every team that reuses it.

</Tab>
<Tab value="Coolify Cloud" icon={Cloud}>

1. Open **Notifications > Email** for the team.
2. Set **Email service** to **Use hosted email service**. No SMTP host, password, or Resend API key is required.
3. Select the events to send by email under **Notification events**.
4. Select **Send test**, enter a recipient address you can access, and send the test.
5. Confirm that the message arrives before relying on the channel for operational alerts.

</Tab>
</Tabs>

## Configure a team provider

Choose SMTP or Resend when this team should use its own email provider instead of the hosted or system-wide configuration.

<Tabs id="notification-email-provider" items={['SMTP', 'Resend']}>
<Tab value="SMTP" icon={ServerCloud}>

Enter the connection details supplied by your SMTP provider.

1. Open **Notifications > Email** and set **Email service** to **Use team email settings**.
2. Under **Email provider**, select **SMTP**. The page shows the settings of the server in the **SMTP server** list. The first server is named `Default`.
3. Optionally, select **Add server**, enter a **Name**, and select a **Template** for your provider. A template fills in **Host**, **Port**, and **Encryption**. Templates are available for PostShiba, Amazon SES (us-east-1), Brevo, Gmail, Mailgun, Mailjet, Microsoft 365, Postmark, Proton Mail, Resend, SendGrid, and Zoho Mail.
4. Enter the settings of the server:

   | Group | Field | Value |
   | :--- | :--- | :--- |
   | **Sender** | **From name** | Name shown in email from this server. Required. |
   | | **From address** | Sender address of this server. It must be on a domain that this server can send from. Required. |
   | **Connection** | **Host** | SMTP hostname, such as `smtp.example.com`. Required. Coolify [checks the host](#smtp-host-checks). |
   | | **Port** | Provider's SMTP port. Common values are `587`, `465`, and `25`. Required. |
   | | **Encryption** | **StartTLS**, **TLS / SSL**, or **None**. Port `587` commonly uses StartTLS and port `465` commonly uses TLS / SSL, but follow your provider's instructions. |
   | **Authentication** | **Username** | SMTP username. Leave it empty only for a relay that does not need a login. Required when the host is the host of a template. |
   | | **Password** | SMTP password. Required when you enter a username. |
   | **Advanced** | **Timeout** | Optional maximum delivery time in seconds. |
   | | **EHLO domain** | Optional fully qualified domain Coolify sends in the SMTP `EHLO` command, such as `coolify.example.com`. Leave it empty to use the system default. |

5. Check the values against your provider's documentation. A mismatched port and encryption option prevents Coolify from connecting.
6. Select **Save changes**. Coolify turns on SMTP and turns off Resend. Until you save complete settings, the page shows **Not active yet**.

If a required field is empty, saving fails with an error such as `From Address is required.`

<Callout type="warning" title="Do not use unencrypted SMTP over an untrusted network">
Choose **None** only when your email provider explicitly requires it and the connection stays on a trusted network. Prefer an encrypted option supported by the provider.
</Callout>

</Tab>
<Tab value="Resend" icon={Rocket2}>

Create a Resend API key and use a sender address on a domain that Resend has verified.

1. Create an API key in the [Resend dashboard](https://resend.com/api-keys).
2. Verify the domain that Coolify will send from in Resend.
3. Open **Notifications > Email** and set **Email service** to **Use team email settings**.
4. Under **Email provider**, select **Resend**.
5. Enter the **Resend API key**, the **From name**, and the **From address**. All three fields are required. The address must be on a domain verified in Resend.
6. Select **Save changes**. Coolify turns on Resend and turns off SMTP.

Resend has its own sender. It does not use the sender of the SMTP servers. With the API, set it with `resend_from_name` and `resend_from_address` in a `PATCH` request to `/api/v1/notifications/email`. When you upgrade from a version before v4.7.0, Coolify copies the old shared sender into these fields.

</Tab>
</Tabs>

## Manage more than one SMTP server

A team can save more than one SMTP server, each with its own sender. Coolify sends email through the server that the **SMTP server** list shows.

- **Add a server:** Select **Add server**, enter a **Name**, optionally select a **Template**, and select **Add server**. Enter the settings, then select **Save changes**. The previous server stays in the list. Select **Cancel** to discard the new server.
- **Switch servers:** Select another server in the **SMTP server** list. Coolify saves the change immediately.
- **Rename a server:** Select the edit icon next to the list, enter the new **Name**, and select **Save**.
- **Delete a server:** Select the delete icon next to the list. Coolify then uses the next server in the list. You cannot delete the only server. To stop using SMTP, select another provider.

## SMTP host checks

Coolify checks the **Host** of a team SMTP server when you save a new host and again before each email. It connects only to the address that it checked, so a later DNS change cannot send the connection to another address.

| Host | Self-hosted Coolify | Coolify Cloud |
| :--- | :--- | :--- |
| Public address | Accepted | Accepted |
| Private network address, such as `10.0.0.0/8` or `192.168.0.0/16`, and Docker service names | Accepted | Refused |
| Loopback address, such as `localhost` or `127.0.0.1` | Refused, unless an instance administrator allows it | Refused |
| Link-local address, such as `169.254.0.0/16` (cloud metadata) | Always refused | Always refused |

To allow a refused internal host on a self-hosted instance, an instance administrator adds it to [**Allowed internal targets**](/core/instance-management/instance-settings#allowed-internal-targets). A loopback host also needs **Localhost targets** set to **Allowed**.

When Coolify refuses a host, the error explains why, for example `The SMTP host points to a local or private address that is not allowed.` For an instance administrator, the error links to the allowed internal targets setting. If the host does not resolve, the error is `The SMTP host could not be resolved.`

These checks apply to the team SMTP servers. The instance email settings under **Settings > Email** do not use them.

## Choose events and verify delivery

Under **Notification events**, select the events to send by email. See [Notification events](/core/notifications/events) for the trigger behind each setting.

Select **Send test**, enter a recipient address you can access, and send the test. Confirm that the message arrives. If it does not, check the provider's activity logs, sender verification, SMTP port access, and spam folder.

## Include commit details in deployment emails

Deployment success and failure emails can show the commit that Coolify deployed. This setting is off by default.

To enable it, open **Notifications > Email** and select **Include commit details in deployment emails** below **Notification events**. Coolify saves the change immediately. Only team admins and owners can change this setting.

When the setting is on, deployment emails show:

| Item | Description |
| :--- | :--- |
| **Commit** | The first 7 characters of the commit SHA. |
| Commit link | The SHA links to the commit page of the Git provider when Coolify can make a link. Coolify uses the URL of the Git source, or the HTTP(S) or SSH repository URL. Bitbucket links use the `/commits/` path. If Coolify cannot make a link, the SHA shows as text. |
| Branch | The branch of the application, after the SHA (for example, `on main`). Pull request preview deployments do not show the branch. |
| **Commit message** | The commit message as plain text. Coolify does not render Markdown or HTML from the message, and it shortens messages that are longer than 1,000 characters. |

If a deployment has no commit SHA and no commit message, the email does not show the commit block. For example, this occurs when the deployment uses `HEAD` instead of a specific commit.

<Callout type="info" title="Email only">
This setting changes only deployment emails. Discord, Telegram, Slack, Pushover, and webhook notifications do not use it.
</Callout>

To change the setting with the API, send `deployment_commit_details_email_notifications` (`true` or `false`) in a `PATCH` request to `/api/v1/notifications/email`. The API token must have the `write` permission. A `GET` request to the same endpoint returns the current value.

## Troubleshoot email delivery

If the test email does not arrive:

1. Confirm that **Email service** and **Email provider** show the provider you want, and that the page does not show **Not active yet**. **Send test** is available only after you save a provider.
2. For SMTP, confirm that the **SMTP server** list shows the server you want. Compare its host, port, and encryption method with the provider's current settings. Also confirm that the Coolify server can make outbound connections on that port.
3. If Coolify refuses the SMTP host, read the error and see [SMTP host checks](#smtp-host-checks).
4. Check whether the provider requires the **From address** or its domain to be verified.
5. Check the provider's delivery or activity logs. An accepted request can still be rejected later because of sender policy or recipient filtering.
6. Check the recipient's spam or junk folder.
7. When using the self-hosted system-wide provider, send a test from **Settings > Email**. If that test also fails, fix the instance provider before troubleshooting the team channel.
